时间窗：2026-05-19。v1-d 主线（PR1-5）已合入 main，PR6（删 grafana）刚清理完。盘点用户反馈的「服务详情·调用统计只有 24h 一档不够用」类小需求。

## 1. 服务/应用/API Key 详情：统计窗口固定 24h，加 7d / 30d / all + 加高调用趋势框

**症状/需求**：

- 服务目录 `/services/:slug` 的「调用统计」tab 三张 KPI 卡 + 调用趋势 + Top 5 应用，窗口**硬编码 24h**（`ServiceDetailPage.vue:115-121`）。
- 应用详情 `/applications/:id` 的「24h 概况」区块同样硬编码 24h（`ApplicationDetailPage.vue:87-93`）。
- API Key 详情 `/api-keys/:id` 的「24h 概况」区块同样硬编码 24h（`ApiKeyDetailPage.vue:54-60`）。
- 调用趋势框现状用 `Sparkline` (`height=64`，spark-wrap min-height=80)，迷你型，看不清拐点 / 周期 / 时间轴；用户想升级到「带坐标轴 + tooltip + y 轴格式」的折线。
- 用户需求：每个详情页支持选 **24h / 7d / 30d / 全部**，KPI 数字与趋势线、Top N 表都跟着切；趋势框加高到 ~240px。

**根因/范围**：

- 后端 `stats` 端点（spec §3.2，`schemas/stats.py:6`）`Range` 字面量只有 `15m | 1h | 24h | 7d`。**缺 30d / all**。
- 现有 bucket 集 `1m | 5m | 1h`：30d × 1h = 720 桶（前端图卡顿）、all × 1h 可能数千桶。**需要新增 1d bucket**，并把 30d / all 的默认 bucket 设为 1d。
- 频率 / 性能：1d bucket 下 30d=30 点、all=N 天（按系统启动日算，N 早期较小）。`call_logs` 已有 `idx_call_logs_ts` (`models.py:200` 的 `ts DESC` 索引)，区间扫描可走索引；不再加新索引。
- "all" 语义：取「自 call_logs 第一条以来」的全部。实现上不去查 `MIN(ts)`（多一次往返、缓存键也尴尬），而是把 `_RANGE_DELTA["all"] = timedelta(days=3650)`（~10 年）作为足够宽的 floor —— `ts >= now-10y` 在本系统语义上等价于「全部」，且与现有 `ts >= :from_ts AND ts < :to_ts` 的 SQL 结构 0 改动。
- TTL：`cache_stats.ttl_for` 现仅对 `15m` 返 10s，其余 30s。30d / all 的数据漂移更慢，30s 缓存依然合理（不另设 longer TTL，保持简单 —— 缓存键已含 range，30d 与 24h 是独立 entry，不会互相污染）。
- 前端 `RangePicker` (`components/charts/RangePicker.vue`) 直接吃 `RANGE_OPTIONS`，扩 RANGE_OPTIONS 即可顺带支持。
- 前端 `TimeseriesChart.xAxisFormatter` (`TimeseriesChart.vue:39`) 现在只 case `15m/1h → HH:mm`、`7d → MM-DD`、其它 `MM-DD HH:mm`。30d / all 用 1d bucket，时间标签 `MM-DD` 更合适；新增分支。
- **范围限定**：本批次只动「单实体详情页的 stats 区块」。仪表盘（`DashboardPage.vue`）的 RangePicker 已经 v-model 在 `Range` 类型上，类型扩字面量后**自动获得**新选项；KPI/趋势/breakdown 都已经按 range 联动，无需额外改动。CallLogListPage / AuditEventListPage 的 sparkline 用本地 `RangeOpt` 类型，**不动**（与 stats Range 解耦的设计）。

**改法**：

## 2. 服务目录：列表端点列改"调用路径"，详情概览加"调用路径"行

**症状/需求**：

- 服务列表「端点」列直接展示后端 `endpoint_url`（如 `http://upstream:9000/mcp`），但这是**上游内网地址**，对终端用户没有可操作性 —— 客户端真正要打的是网关入口 `/<host>/mcp/<slug>`。当前 UI 等于把内部 plumbing 暴露在最显眼的列上、还遮住了客户实际要 copy-paste 的串。
- 用户需求：列表「端点」列改为「通过本系统使用 MCP 服务的路径」（即网关 URL），详情页保留 `endpoint_url`（运维/调试需要）并新增「调用路径」一行。

**根因/范围**：

- 网关入口路径硬规约为 `POST /mcp/{slug}`（`services/gateway/src/gateway/routers/mcp.py:14,44`）。nginx (`nginx/nginx.conf:31`) 已把 `/mcp/` 反代到 gateway upstream；dev 模式 `vite.config.ts` 也代理 `/mcp` 到本机 nginx。
- → 前端可直接以 `${window.location.origin}/mcp/${slug}` 构造 URL，无需后端新增字段、无需读环境变量。这条规约在 v1 / v1-d 都没变过，前端写死 `/mcp/` 路径是合理的（若以后 nginx 调整 location，需要同步本前端的 helper）。
- 不在「调用路径」上暴露 `endpoint_url`：上游 URL 是部署细节、可能在 VPN/内网，**正常 viewer 不该看到完整后端地址**也是合理的轻度信息隐藏。本次详情页仍保留 `endpoint_url` 行（admin/operator/viewer 都能看），是个权衡 —— 完全隐藏会让运维排障时跳到 DB 查 endpoint_url，不便；当前所有角色都能进详情页（路由没设 `roles`），收紧粒度属于 v2 范围，不动。
- 注册对话框「端点 URL」字段含义保持不变（用户输入的就是后端 endpoint，gateway 转发目标）—— 不改 label / placeholder。

**改法**：

- `services/web/src/utils/format.ts`：新增
  ```ts
  export function gatewayUrl(slug: string): string {
    if (typeof window === 'undefined') return `/mcp/${slug}`;
    return `${window.location.origin}/mcp/${slug}`;
  }
  ```
  SSR fallback 不会真用到（项目 CSR-only），但放进去免得未来某天测试环境 prerender 时炸。

- `services/web/src/views/services/ServiceListPage.vue`：
  - import 增加 `gatewayUrl`。
  - 删除 `<el-table-column prop="endpoint_url" label="端点" ...>`。
  - 在该位置插入：
    ```html
    <el-table-column label="调用路径" min-width="280" show-overflow-tooltip>
      <template #default="{ row }: { row: McpService }">
        <span class="mono">{{ gatewayUrl(row.slug) }}</span>
      </template>
    </el-table-column>
    ```
  - 注册对话框「端点 URL」字段**不动**，那里仍是输入 upstream 的入口。

- `services/web/src/views/services/ServiceDetailPage.vue`：
  - import 增加 `gatewayUrl`。
  - 在 `overview__row` "端点 URL" **之前**插入新行：
    ```html
    <div class="overview__row">
      <div class="overview__label">调用路径</div>
      <div class="overview__value mono">
        {{ gatewayUrl(service.slug) }}
        <CopyButton :text="gatewayUrl(service.slug)" />
      </div>
    </div>
    ```
  - 「端点 URL」行**不动**：保留给运维/排障，区分语义。

i18n 不改（项目无国际化，沿用中文硬编码）。

**测试**：

不新增单测：纯展示型改动，逻辑只有 `gatewayUrl` 字符串拼接 + 一处 `typeof window` 兜底，ROI 低于已有 `format.ts` 的同类 helper（`formatBytes` / `formatDuration` 也没测）。

1. 服务列表表头出现「调用路径」列，每行展示 `https://<host>/mcp/<slug>`（hover 看 tooltip 拿完整串）；不再看到 `http://upstream:...` 这类内部地址。

**未覆盖**：

## 5. 登录后默认落地仪表盘

**症状/需求**：登录系统后展示的是「服务目录」，用户希望默认落地「仪表盘」。

**根因/范围**：

- `services/web/src/router/index.ts:22-25` 把 `/` 重定向到 `ServiceList`（v1-d PR3 起的策略，inline 注释明示 "保持默认登录后落地 /services；仪表盘作为可单独导航的页面"）。
- 登录页 `LoginPage.vue:29-30`：`router.push(route.query.redirect ?? '/')` —— 没带 redirect query 时落到 `/`，再被路由 redirect 链接到 ServiceList。
- 策略反转点很小：改一行 redirect 目标即可。深链场景（`/login?redirect=/services/foo`）走原路径，**不**受影响。
- `Dashboard` 路由 `meta: { requiresAuth: true }`，无 `roles` 限制（admin / operator / viewer 都能访问），与 ServiceList 同。落地切换不踩权限墙。

**改法**：

`services/web/src/router/index.ts`：

- `path: '/'` 的 redirect 由 `{ name: 'ServiceList' }` 改为 `{ name: 'Dashboard' }`。
- 把上方的注释由「保持默认登录后落地 /services；仪表盘作为可单独导航的页面，路径 /dashboard。」改为「默认登录后落地 /dashboard（仪表盘）；服务目录通过侧边栏导航进入。」与新策略一致。

不动 `LoginPage.vue`：fallback `'/'` 仍然合适，policy 集中在 router 表里。

**测试**：

无新增。`tests/unit/` 不覆盖 router redirect 配置（属于纯声明）。

**验证**（待用户在浏览器跑）：

1. 退出登录 → `/login` → 输入凭据 → 落到 `/dashboard`，仪表盘加载完毕。
2. 已登录状态访问 `<host>/` → 自动跳 `/dashboard`（不再是 `/services`）。
3. 未登录访问 `/services/xxx` → bounce 到 `/login?redirect=/services/xxx` → 登录后回到 `/services/xxx`（深链回跳保留）。
4. 侧边栏导航点「服务目录」仍可手动进入。

**未覆盖**：

- 不同角色"应该落到不同首页"的更精细策略（如 viewer 落 Dashboard、operator 落 ServiceList）—— 本次不分角色，全员落 Dashboard。
- 用户偏好持久化（"上次访问的页面"作为下次落地）—— 不引入 localStorage 状态，避免不可预期跳转。
