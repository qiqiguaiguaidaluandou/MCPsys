# 详情页调用统计窗口扩展

时间窗：2026-05-19。v1-d 主线（PR1-5）已合入 main，PR6（删 grafana）刚清理完。盘点用户反馈的「服务详情·调用统计只有 24h 一档不够用」类小需求。

不走 spec/plan。条目结构：症状/需求 → 根因/范围 → 改法 → 测试 → 验证 → 未覆盖。

---

## 1. 服务/应用/API Key 详情：统计窗口固定 24h，加 7d / 30d / all + 加高调用趋势框

**症状/需求**：

- 服务目录 `/services/:slug` 的「调用统计」tab 三张 KPI 卡 + 调用趋势 + Top 5 应用，窗口**硬编码 24h**（`ServiceDetailPage.vue:115-121`）。
- 应用详情 `/applications/:id` 的「24h 概况」区块同样硬编码 24h（`ApplicationDetailPage.vue:87-93`）。
- API Key 详情 `/api-keys/:id` 的「24h 概况」区块同样硬编码 24h（`ApiKeyDetailPage.vue:54-60`）。
- 调用趋势框现状用 `Sparkline` (`height=64`，spark-wrap min-height=80)，迷你型，看不清拐点 / 周期 / 时间轴；用户想升级到「带坐标轴 + tooltip + y 轴格式」的折线。
- 用户需求：每个详情页支持选 **24h / 7d / 30d / 全部**，KPI 数字与趋势线、Top N 表都跟着切；趋势框加高到 ~240px。

**根因/范围**：

- 后端 `stats` 端点（spec §3.2，`schemas/stats.py:6`）`Range` 字面量只有 `15m | 1h | 24h | 7d`。**缺 30d / all**。
- 现有 bucket 集 `1m | 5m | 1h`：30d × 1h = 720 桶（前端图卡顿）、all × 1h 可能数千桶。**需要新增 1d bucket**，并把 30d / all 的默认 bucket 设为 1d。
- 频率 / 性能：1d bucket 下 30d=30 点、all=N 天（按系统启动日算，N 早期较小）。`call_logs` 已有 `idx_call_logs_ts` (`models.py:200` 的 `ts DESC` 索引)，区间扫描可走索引；不再加新索引。
- "all" 语义：取「自 call_logs 第一条以来」的全部。实现上不去查 `MIN(ts)`（多一次往返、缓存键也尴尬），而是把 `_RANGE_DELTA["all"] = timedelta(days=3650)`（~10 年）作为足够宽的 floor —— `ts >= now-10y` 在本系统语义上等价于「全部」，且与现有 `ts >= :from_ts AND ts < :to_ts` 的 SQL 结构 0 改动。
- TTL：`cache_stats.ttl_for` 现仅对 `15m` 返 10s，其余 30s。30d / all 的数据漂移更慢，30s 缓存依然合理（不另设 longer TTL，保持简单 —— 缓存键已含 range，30d 与 24h 是独立 entry，不会互相污染）。
- 前端 `RangePicker` (`components/charts/RangePicker.vue`) 直接吃 `RANGE_OPTIONS`，扩 RANGE_OPTIONS 即可顺带支持。
- 前端 `TimeseriesChart.xAxisFormatter` (`TimeseriesChart.vue:39`) 现在只 case `15m/1h → HH:mm`、`7d → MM-DD`、其它 `MM-DD HH:mm`。30d / all 用 1d bucket，时间标签 `MM-DD` 更合适；新增分支。
- **范围限定**：本批次只动「单实体详情页的 stats 区块」。仪表盘（`DashboardPage.vue`）的 RangePicker 已经 v-model 在 `Range` 类型上，类型扩字面量后**自动获得**新选项；KPI/趋势/breakdown 都已经按 range 联动，无需额外改动。CallLogListPage / AuditEventListPage 的 sparkline 用本地 `RangeOpt` 类型，**不动**（与 stats Range 解耦的设计）。

**改法**：

后端 `services/control_plane/src/control_plane/schemas/stats.py`：

- `Range` 字面量加 `"30d" | "all"` → `Literal["15m", "1h", "24h", "7d", "30d", "all"]`。
- `Bucket` 字面量加 `"1d"` → `Literal["1m", "5m", "1h", "1d"]`。

后端 `services/control_plane/src/control_plane/routers/stats.py`：

- `_RANGE_DELTA` 加两行：
  ```python
  "30d": timedelta(days=30),
  "all": timedelta(days=3650),   # 等价"无下界"；call_logs 不会真有 10 年前的行
  ```
- `_DEFAULT_BUCKET` 加两行：
  ```python
  "30d": "1d",
  "all": "1d",
  ```
- `_floor_to_bucket` 增加 `1d` 分支：
  ```python
  if bucket == "1d":
      return ts.replace(hour=0, minute=0, second=0, microsecond=0)
  ```
- `_bucket_step` 字典加 `"1d": "1 day"`。
- `_bucket_expr` 加分支：
  ```python
  if bucket == "1d":
      return "date_trunc('day', ts) AS bucket_ts"
  ```
- 其它代码（SQL 模板、`pick_filter`、`cache_or_compute` 调用等）不动 —— `_RANGE_DELTA` / `_DEFAULT_BUCKET` 是 dict 而非闭区间枚举，新键加进去即被各端点使用。
- `ttl_for` 不动：现在的「15m=10s / else=30s」对 30d/all 仍然合理。

后端测试 `services/control_plane/tests/test_stats_overview.py`：

- 新增 `test_overview_30d_and_all_ranges`：落 3 条 call_log（now-3h / now-3d / now-40d），分别请求 `range=24h` → 1 条、`range=7d` → 2 条、`range=30d` → 2 条、`range=all` → 3 条。覆盖 30d/all 两个新枚举值通过路由校验、覆盖窗口边界。
- `test_overview_invalid_range_422` 已存在，无需改（`foo` 仍然 422）。

后端测试 `services/control_plane/tests/test_stats_timeseries.py`：

- 新增 `test_timeseries_30d_default_bucket`：落 1 条 call_log 在 now-5d，请求 `range=30d&metric=calls` → 200，响应 `bucket == "1d"`，points 长度 == 30，含且仅含 1 个非零桶。
- 新增 `test_timeseries_all_with_1d_bucket`：落 1 条 call_log 在 now-100d，请求 `range=all&metric=calls` → 200，响应 `bucket == "1d"`，points 非空，含且仅含 1 个非零桶。
- 不另测 `bucket=1d` 显式入参（默认 bucket 已覆盖；防止 1d 与 1h 等组合做矩阵爆炸测试）。

后端测试 `services/control_plane/tests/test_stats_breakdown.py`：

- `range=all` 不另测 breakdown（与 30d 唯一区别是 from_ts 更早；breakdown SQL 与 from_ts 无关，覆盖一次足够）。

前端 `services/web/src/api/stats.ts`：

**未覆盖**：

- **range > 30d 时 Top N 排行**：30d / all 数据量较大，前端 limit=5 仍生效，但**「其它」桶**（spec §3.2.3 的 `BreakdownOther`）可能变得很大；本次不在 detail 页展示 other（KpiCard 侧已显示总 calls，用户可自行心算）。后续如要在 BarChart 旁加 "其它 N 次（占比 X%）" 一行，单独条目。
- **`all` 窗口下 `from` 字段**：响应里 `from = to - 10y`（即 ~2016），UI 不直接展示 `from`，无误导。若以后某处把 `from` 渲染到页面（目前没有），需要特判 all 转成「自上线以来」之类文案。
- **首次进入 stats tab 的预加载**：watch 触发条件改为 `tab===stats && statsLoaded !== statsRange`，意味着切到 tab 才发请求（与现状一致）。无预加载 → 切 tab 时短暂 loading。可接受。
- **缓存命中率退化**：30d / all 是冷查询，首次 miss；30s TTL 之内连续切换有 hit。整体读 QPS 提升幅度小，不另做缓存策略调优。
- **call_logs 表 30 天清理对 `all` 的影响**：若启用 `body 30 天 NULL 化`（spec 提及但 MVP 未实现的清理任务）后，metadata 行仍在；如果未来再加「90 天 / 180 天物理删除」清理，`all` 实际等价 90/180 天。届时 RangePicker 上需要把 "全部" 改成更准确的字面（如 "180 天"）。当前没有清理任务，不动。
- **API Key / Application 详情页的 stats 区块本来就没有 Top N 表**（只有 KPI + 趋势 / 双趋势），保持原状，不顺手加。
