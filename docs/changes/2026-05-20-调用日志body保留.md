# 调用日志 body 保留 worker 落地

时间窗：2026-05-20。延续 `2026-05-19-服务健康检查实现.md` §开头点出的反模式——「schema / 注释 / spec 都齐，就是没有 writer」。这次轮到数据保留：`CallLog` 的 docstring 白纸黑字写着 "Body fields are nulled after 30 days"，spec §7 也定了口径，但全仓库 grep 不到任何清理代码。后果比健康检查更隐蔽：`call_logs` 带着完整 request/response body 无限增长，既是存储/索引膨胀问题，也是敏感内容永久留存的隐私问题。

条目结构沿用：症状/需求 → 根因/范围 → 改法 → 测试 → 验证 → 未覆盖。

## 1. control-plane 启动 body 保留 worker，周期性清空超期调用日志的 body 列

**症状/需求**：

- `packages/mcpsys_shared/src/mcpsys_shared/models.py` 的 `CallLog` docstring 声称 "Body fields are nulled after 30 days"，但这只是注释，没有任何代码执行它。
- spec `docs/specs/2026-04-30-mcp-management-system-design.md` §7（行 57 / 369）定下数据保留口径：**调用 metadata 永久；调用 body（request_body / response_body）30 天后置 NULL；audit_events 永久**。
- 当前 grep `retention` / `cleanup` / `request_body = NULL` 在 `services/` `packages/` `scripts/` 下 **0 个执行点**。
- 用户需要：body 真的按 spec 在 N 天后清空，让 `call_logs` 不再无限堆积明文 body（spec 估算 100 QPS ≈ 860 万行/天，每行两列 body 各上限 64KB）。

**根因/范围**：

- 采用方案：**asyncio 原生 loop**，与 `health_checker` 完全同形态（同会话已确立的模式），不引 APScheduler。理由同健康检查那篇：全程已 async、任务简单（固定周期、无 cron、无持久化、无 backfill）、一个 `create_task(loop)` + cancel-on-shutdown 即可。
- **只清 body，不删行**：spec 明确 metadata 永久。worker 做的是 `UPDATE ... SET request_body=NULL, response_body=NULL`，绝不 `DELETE`。
- **不做月度分区**：spec AD-3 提到 `call_logs` 可按月分区 + detach 旧分区，但那是「行级 retention / 海量扩展」的设计；本次的保留口径是「body 置 NULL、metadata 永久」，分区不是它的前置条件。分区是独立的扩展工作，超出本批次范围，文档化为未覆盖。
- 不在 gateway 跑（AD-4 同理：gateway 多实例无状态，重复清理纯属空跑、互相打架）。
- 不动 `call_logs` 表结构 / 写入路径 / 任何查询路由。唯一 schema 变化是**新增一个部分索引**（见下）支撑清理扫描。

**关于部分索引**：

清理查询是 `WHERE ts < cutoff AND (request_body IS NOT NULL OR response_body IS NOT NULL)`。若只靠现有 `ix_call_logs_ts`，稳态下最旧的行大多已被清空，按 ts 升序扫描会先趟过海量「已 NULL」的老行再够到少量未清的，代价正比于全表。

解决：新增**部分索引** `ix_call_logs_body_unpurged ON call_logs (ts) WHERE request_body IS NOT NULL OR response_body IS NOT NULL`。它只含「body 尚未清空」的行；行一旦被清空就掉出索引。于是 `ts < cutoff` 在这个部分索引上的范围扫描，代价正比于「待清理积压量」而非全表行数——`call_logs` 再大，每轮清理也不退化。

**改法**：

`services/control_plane/src/control_plane/settings.py`：

- 新增四个配置：
  ```python
  retention_enabled: bool = Field(default=True)
  call_log_body_retention_days: int = Field(default=30, ge=1)
  retention_interval_seconds: int = Field(default=3600, ge=60)
  retention_batch_size: int = Field(default=5000, ge=1)
  ```
- `retention_enabled` 给测试用（与 `health_check_enabled` 同款隔离开关）。
- interval 默认 1h：30 天的截止边界移动很慢，每小时扫一次绰绰有余。

新建 `services/control_plane/src/control_plane/retention.py`（核心）：

- `async def run_retention_round(session_factory, *, retention_days, batch_size) -> int`
  - `cutoff = now() - retention_days`
  - 循环执行分批 UPDATE，每批一个独立 session + commit：
    ```sql
    UPDATE call_logs
    SET request_body = NULL, response_body = NULL
    WHERE id IN (
        SELECT id FROM call_logs
        WHERE ts < :cutoff
          AND (request_body IS NOT NULL OR response_body IS NOT NULL)
        ORDER BY ts
        LIMIT :batch
    )
    ```
  - `affected < batch` ⇒ 已无更多超期行，跳出；返回本轮清空的总行数。
  - 子查询 `ORDER BY ts` + 谓词与部分索引完全对齐 ⇒ 走 `ix_call_logs_body_unpurged`，最旧的先清。
  - **为什么分批 + 逐批提交**：一次清几百万行会拿很长的行锁、撑大 WAL、阻塞 autovacuum。每批限量、独立事务提交，把单次写事务控制在可控范围；首次部署面对历史积压也是逐批啃完，不会一口气锁死。
- `async def retention_loop(session_factory) -> None`
  - `while True: try run_retention_round; except Exception: logger.exception(); await asyncio.sleep(interval)`
  - try/except 必须：单轮异常（如 DB 短暂断连）不能让 loop 死。

`services/control_plane/src/control_plane/main.py`：

- `lifespan` yield 前，紧随 health_task 之后：
  ```python
  app.state.retention_task = None
  if settings.retention_enabled:
      from .retention import retention_loop
      app.state.retention_task = asyncio.create_task(retention_loop(app.state.session_factory))
  ```
- `finally` 改为统一遍历 cancel 两个 task：
  ```python
  for task in (app.state.health_task, app.state.retention_task):
      if task is not None:
          task.cancel()
          with contextlib.suppress(asyncio.CancelledError):
              await task
  ```

`packages/mcpsys_shared/src/mcpsys_shared/models.py`：

- `CallLog.__table_args__` 增部分索引：
  ```python
  Index(
      "ix_call_logs_body_unpurged",
      "ts",
      postgresql_where=text("request_body IS NOT NULL OR response_body IS NOT NULL"),
  )
  ```
- docstring 改为如实描述：metadata 永久；body 由 `control_plane.retention` 在 `call_log_body_retention_days`（默认 30）后置 NULL；行永不删除。

`services/control_plane/alembic/versions/0007_call_logs_body_unpurged_index.py`（新建）：

- 用 `CREATE INDEX CONCURRENTLY IF NOT EXISTS`，包在 `op.get_context().autocommit_block()` 里。
- **为什么 CONCURRENTLY**：`call_logs` 是 gateway 高频写入的表，普通 `CREATE INDEX` 的 SHARE 锁会阻塞 telemetry 写入；CONCURRENTLY 不锁写。它不能在事务里跑，alembic 用 `autocommit_block()` 临时跳出迁移事务。downgrade 同样 `DROP INDEX CONCURRENTLY IF EXISTS`。

**测试** `services/control_plane/tests/test_retention.py`（新建，直接调 `run_retention_round`，与 `test_health_checker` 直调 `run_health_check_round` 同风格）：

- `test_purges_bodies_past_cutoff`：插 1 条 40 天前的行 → 跑一轮 → 两个 body 列变 NULL、行仍在、metadata（service_id/status）不变、返回 1。
- `test_keeps_bodies_within_cutoff`：插 1 条 5 天前的行 → body 原样保留、返回 0。
- `test_idempotent_already_nulled_not_recounted`：超期行清过一次后再跑，第二轮返回 0（`body IS NOT NULL` 谓词过滤）。
- `test_batches_until_drained`：插 5 条超期行、`batch_size=2` → 单轮循环分批清完全部 5 条。
- `test_empty_db_no_op`：空库返回 0、不抛错。

**验证**（待用户在测试环境跑）：

1. 把 `RETENTION_INTERVAL_SECONDS` 调小（如 60）、`CALL_LOG_BODY_RETENTION_DAYS` 调小（如 0 或临时改一行 ts 到很久以前），观察日志出现 `retention: nulled bodies on N call_logs rows`。
2. `psql -c "SELECT count(*) FROM call_logs WHERE ts < now() - interval '30 days' AND (request_body IS NOT NULL OR response_body IS NOT NULL)"` → 应稳定收敛到 0。
3. 同条件下 `SELECT count(*) FROM call_logs WHERE ts < now() - interval '30 days'`（不带 body 条件）→ 行数不减（metadata 永久，只清 body 不删行）。
4. `\d call_logs` 确认 `ix_call_logs_body_unpurged` 存在；`EXPLAIN` 清理子查询确认走该部分索引。
5. 迁移到生产时 `alembic upgrade head` 建索引期间 gateway 写入不被阻塞（CONCURRENTLY 生效）。

**未覆盖**：

- **行级 retention / 月度分区**：本批次只清 body，metadata 永久，行永不删除（遵 spec）。`call_logs` 行数仍单调增长；spec AD-3 的月度分区是独立扩展工作，未实现。若未来 metadata 行数本身成问题，再上分区 + detach。
- **多 control-plane 实例**：当前 compose 单实例。若 scale=2，两实例都跑 retention loop → 重复扫描、重复 UPDATE（幂等、无脏数据，但浪费）。修法与健康检查一致：Redis 分布式锁选 leader。文档化为已知 latent。
- **首次部署的大积压**：若生产已积压海量超期 body，首轮 `run_retention_round` 会一直分批清到清完才返回（每批独立提交，不锁死，但单轮耗时可能长）。可临时调大 `retention_batch_size` 或接受它在后台慢慢追平。
- **audit_events 不在范围**：`audit_events` 无 body 列、spec 标注永久保留，本 worker 不碰。
- **关停时正在跑的轮次被 cancel**：lifespan finally 的 `cancel()` 触发 `CancelledError`，正在进行的批次若未 commit 则整批回滚（asyncpg 行为），已 commit 的批次已落盘——无脏数据。下次启动续清即可。
- **NULL 后的物理空间回收**：`UPDATE ... SET ... NULL` 只是逻辑清空，dead tuple 的物理空间靠 autovacuum 回收，TEXT 大字段进 TOAST 表。本批次不主动 `VACUUM FULL`（会锁表），交给 autovacuum。
