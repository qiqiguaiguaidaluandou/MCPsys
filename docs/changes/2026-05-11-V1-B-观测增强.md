## 1. 调用日志详情页 + body 查看（V1-B 主题 B）

**症状/需求**：`CallLogListPage.vue` 只能看 metadata 列（时间 / status / duration / tool_name 等）；`call_logs.request_body` / `response_body` 字段 gateway 已经在写库，但 UI 完全没暴露。排障时常常需要看「这次失败调用具体发了什么 / 后端返了什么」，目前只能登 postgres 直接 `SELECT request_body FROM call_logs WHERE id='...'`。

**根因/范围**：

- 后端只有 `GET /api/v1/call-logs`（列表），无单条详情端点；列表 `CallLogOut` schema 也刻意去掉了 body 字段（避免大 payload 灌进列表）。
- 前端只有 `CallLogListPage.vue`，无 detail 页、无单条 fetch API。
- 列表行无任何点击交互——既不能 router-push 也不能展开。
- 本次范围：补一个 admin/operator 可见的详情端点 + 详情页 + 列表 → 详情的入口（操作列「详情」按钮，与 services / users 等列表保持一致风格）。
- body 字段过期清理：spec 设计 30 天后 `UPDATE call_logs SET request_body=NULL, response_body=NULL`。当前**没有自动清理任务**（MVP 已知限制，deployment.md §11 标注）。本次详情页要正确处理 body 为 NULL 的情况，但**不**做清理脚本。
- 权限：与列表一致——admin / operator，**不**给 viewer（spec call_logs.py:38 注释明确：viewer 全局只读不应看跨 application 的 body 内容；per-tenant scoping 是 v2 任务）。

**改法**：

后端 `services/control_plane/src/control_plane/routers/call_logs.py`：
- 新增 `CallLogDetail(BaseModel)` schema，在 `CallLogOut` 基础上扩字段：
  `service_version: str | None`、`request_id: str | None`、`error_message: str | None`、`request_body: str | None`、`response_body: str | None`、`client_ip: str | None`
  （列表 `CallLogOut` 保持精简，**不**改）
- 新增 `@router.get("/{call_id}", response_model=CallLogDetail, dependencies=[Depends(require_role("admin", "operator"))])` 端点 `get_call_log(call_id: UUID, db)`：
  `await db.get(CallLog, call_id)`，None → `HTTPException(404, "调用日志不存在")`
  正常 → `CallLogDetail.model_validate(row)`
- 不接入审计（READ 端点，与 audit_events 设计正交，spec §3.4 已明确）

后端测试 `services/control_plane/tests/test_call_logs.py`：

## 2. Grafana 监控扩展：P50/P95/P99 + by caller / by tool（V1-B 主题 C）

**症状/需求**：现有 dashboard `mcp-overview.json` 有 4 个面板（24h 总数 / 错误率 / Top 服务 / 每分钟调用），覆盖「整体健康」维度但缺：
- 延迟分位（运维要看「99 分位是否抬头」、不是均值）
- 按调用方分布（哪个 application 拉走最多流量）
- 按 tool 分布（哪个 tool 被调最多）

spec §6 v1 第 5 条明确写「监控仪表盘扩展：延迟分位（P50/P95/P99）、按调用方分布、按 tool 分布」。

**根因/范围**：

- 不是 bug，是建表后没补面板。`call_logs.duration_ms` / `application_id` / `tool_name` 字段全在，Grafana Postgres datasource 也接好了，只差 SQL + JSON。
- 范围：在现有 `mcp-overview.json` 追加 3 个面板（不另建 dashboard——避免 dashboard 增多导致首页找不到东西；4 + 3 = 7 个面板仍可控）。
- 维度选 application_id 而非 api_key_id：api_key 是签发凭据、application 是逻辑应用，应用层视角更适合「谁在拉量」分析。
- 时间窗：与现有面板一致用 `$__timeFrom() AND $__timeTo()`（Grafana 标准时间宏），让 dashboard 顶部时间选择器统一控制。
- 延迟分位用 `percentile_cont` (postgres 内建)，不引外部聚合。

**改法**：

改 `grafana/provisioning/dashboards/mcp-overview.json`：

- 在 panels 数组追加 3 个 panel：

**Panel 5: 延迟分位（P50/P95/P99）—— timeseries**
- type: `timeseries`，title: `Latency percentiles (P50/P95/P99)`
- 单 query：
  ```sql
  SELECT
    time_bucket('1 minute', ts) AS time,
    percentile_cont(0.50) WITHIN GROUP (ORDER BY duration_ms) AS p50,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95,
    percentile_cont(0.99) WITHIN GROUP (ORDER BY duration_ms) AS p99
  FROM call_logs
  WHERE $__timeFilter(ts)
  GROUP BY time_bucket('1 minute', ts)
  ORDER BY time
  ```
  > 注：若 postgres 没装 timescaledb 的 `time_bucket`，改用 `date_trunc('minute', ts)` —— 部署环境是 `postgres:16-alpine` 原版，**用 date_trunc**。所以最终 SQL：
  ```sql
  SELECT
    date_trunc('minute', ts) AS time,
    percentile_cont(0.50) WITHIN GROUP (ORDER BY duration_ms) AS p50,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95,
    percentile_cont(0.99) WITHIN GROUP (ORDER BY duration_ms) AS p99
  FROM call_logs
  WHERE $__timeFilter(ts)
  GROUP BY date_trunc('minute', ts)
  ORDER BY time
  ```
- fieldConfig: `unit: ms`，3 条线分别命名 P50 / P95 / P99
- gridPos: w=24 h=8（占满一整行，放总数/错误率那两个 stat 行之下）

**Panel 6: Top callers (24h) by application —— barchart**
- type: `barchart`，title: `Top callers (application) by calls`
- query：
  ```sql
  SELECT
    COALESCE(a.name, '(no-app)') AS application,
    COUNT(*) AS calls
  FROM call_logs cl
  LEFT JOIN applications a ON a.id = cl.application_id
  WHERE $__timeFilter(cl.ts)
  GROUP BY a.name
  ORDER BY calls DESC
  LIMIT 10
  ```
- 与现有 panel 3 (`Top services by calls`) 结构对称。`LEFT JOIN` 保留 `application_id IS NULL` 行（聚合到 `(no-app)`），避免被 INNER JOIN 静默丢掉。
- gridPos: w=12 h=8

**Panel 7: Top tools (24h) —— barchart**
- type: `barchart`，title: `Top tools by calls`
- query：
  ```sql
  SELECT
    COALESCE(tool_name, '(no-tool)') AS tool,
    COUNT(*) AS calls
  FROM call_logs
  WHERE $__timeFilter(ts) AND tool_name IS NOT NULL
  GROUP BY tool_name
  ORDER BY calls DESC
  LIMIT 10
  ```
- gridPos: w=12 h=8（与 panel 6 同行）

**布局调整**：现有 4 个 panel 排在 row 0-1（stat * 2 在顶，barchart + timeseries 在下）。新加 3 个 panel 在 row 2-3。具体 gridPos 由文件落盘时确定，保持「stat 在顶、percentile timeseries 在中、distribution barcharts 在底」的层次感。

**title 改为「MCP Overview & Latency」**（可选）反映扩了延迟维度——本次**不改 title**，保持现有 title 稳定避免外链断（如果有人 bookmark 了 `/grafana/d/mcpsys-overview/mcp-overview`，title 不动 slug 不变）。

**测试**：

- 无单元测试可加（Grafana JSON 是配置而非代码）
- 把 JSON `python3 -m json.tool` 校验语法合法
- 进 Grafana UI 手工验证（见验证段）

**验证**（2026-05-11 执行结果）：

- 静态：`python3 -m json.tool grafana/provisioning/dashboards/mcp-overview.json > /dev/null` → **JSON OK**，panels 数量 4 → 7
- 部署后手工（待用户在浏览器跑）：
  ① Grafana → MCPsys → MCP Overview 打开
  ② 7 个 panel 都渲染
  ③ Latency 面板有 P50/P95/P99 三条线（数据足够时）
  ④ Top callers 显示 application.name（已删 app 或 application_id 为空回退到 `(no-app)`）
  ⑤ Top tools 各显示 ≤ 10 行 bar

**执行中清掉的 1 处文档冗余**：Panel 7 doc 同时写了 `WHERE tool_name IS NOT NULL` 和 `COALESCE(tool_name, '(no-tool)')`；既然 WHERE 已过滤掉 NULL，COALESCE 是死代码。实际 SQL 只保留 WHERE，去掉 COALESCE。
