## 1. control-plane 启动 health checker，状态变化进 audit；详情页「健康历史」接 audit 渲染

**症状/需求**：

- 服务列表「健康」列永远显示灰色（`unknown`）；详情页「最近健康检查」永远 "-"；「健康历史」tab 是占位文字 "健康检查历史（v1）。"。
- 用户需要：服务挂没挂这个**最基本的运维信号**真的工作起来；「健康历史」tab 真的列出状态变化的时间线。
- 同会话 §7 已验证「数据库/schema/UI 都齐、就是没有 writer」是这个项目反复出现的反模式；这次按 spec §4.3 流程 C 一次性补齐。

**根因/范围**：

- DB / schema / UI 全在；spec `docs/specs/2026-04-30-mcp-management-system-design.md` §4.3 明确写：「control plane 启动后台 scheduler（APScheduler），每 30s 对所有 status=active 的服务并发执行：调后端 POST /mcp 发 initialize 心跳；写回 mcp_services.health_status + last_health_check_at；状态变化时写一条 audit_events，便于排障'何时挂的'」。
- 当前 grep `health_status =` / `last_health_check_at =` 在 `services/` `packages/` 下 **0 个写入点**；`apscheduler>=3.10` 在 `services/control_plane/pyproject.toml` 已声明（就是给本特性留的，但从未引入）。
- 采用方案：**asyncio 原生 loop**，不引 APScheduler。理由：
  - 已经全程 async（FastAPI lifespan、AsyncSession、httpx.AsyncClient）
  - 任务很简单 —— 周期固定 30s、无 cron 表达式、无持久化、无 backfill
  - APScheduler 引入意味着多一套依赖与配置面、和 lifespan 的协调要写额外胶水
  - 一个 `asyncio.create_task(loop)` + cancel-on-shutdown 完事
- 「健康历史」**不另建表**：直接复用 `audit_events`。
  - target_type=`mcp_service`，target_id=`<service_id_str>`，action=`service.health_change`，before/after 各存 `{"health_status": "...", "slug": "..."}`（轻量，不走 `model_to_dict` 全字段以免噪声）
  - 详情页查询走新端点 `GET /api/v1/services/{slug}/health-history`（理由见下），不直接调 `/audit-events`
- 不修改 `audit_events` 表结构 / 路由 / 权限。
- 不在 gateway 做（spec AD-4 明确禁止，重复探活无意义）。

**关于权限隔离**：

`/api/v1/audit-events` 仅 `admin` 可见（`routers/audit_events.py:38`）。但服务详情页对 `admin / operator / viewer` 全开放（路由 `meta` 无 `roles` 限制）。如果详情页前端直接调 `/audit-events`，viewer 会 403，整个 tab 砸。

解决方案：新增 `GET /api/v1/services/{slug}/health-history`，三角色都能访问，**服务端**查 `audit_events`、只返回该服务的健康变化事件 + 收窄字段（不返回 actor / IP，避免次生信息泄露）。

后端新建 `services/control_plane/src/control_plane/health_checker.py`（核心）：

- `async def probe_service(client, endpoint_url) -> HealthStatus`
  - POST `endpoint_url` body `{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}`
  - timeout = `settings.health_check_timeout_seconds`
  - 返回分类：
    - **healthy**：HTTP 2xx 或 4xx（4xx = "服务有响应但拒绝了这个探活请求"，仍意味着上游存活；服务端没坏）
    - **unhealthy**：HTTP 5xx、connection refused / timeout / DNS failure / TLS error 等所有 `httpx.RequestError` 与 `httpx.TimeoutException`
  - 不抛异常（吃掉一切，函数总是返回一个 HealthStatus）
- `async def run_health_check_round(session_factory) -> None`
  - 开 session 查 `select(McpService).where(status=active)`；空列表直接 return
  - 开 `httpx.AsyncClient()` + `asyncio.Semaphore(settings.health_check_concurrency)`，对每个服务并发 `probe_one` → 收集 `(svc_id, old_status, new_status)`
  - **新开第二个 session** 写回：用 `session.get(McpService, id)` 拿到 tracked 实例 → 总是更新 `last_health_check_at = now()`、`new_status != old_status` 时 update `health_status` 并 `audit_log(action=SERVICE_HEALTH_CHANGE)`
  - `await session.commit()` 一次性提交
  - 为什么两段 session？第一段并发 probe 时不能持有 session（async ssession 不能多 await 跨边界使用）；第二段写回是单线程顺序 UPDATE，自然事务边界。
- `async def health_check_loop(session_factory) -> None`
  - `while True: try run_health_check_round; except Exception: logger.exception(); await asyncio.sleep(interval)`
  - **try/except 必须**：单轮异常不能让 loop 死掉；典型如 DB 短暂断连
- 不实现 jitter / staggered start（30s × N 服务并发够稀疏）。

后端 `services/control_plane/src/control_plane/main.py`：

- `lifespan` 内 yield 前：
  ```python
  app.state.health_task = None
  if settings.health_check_enabled:
      from .health_checker import health_check_loop
      app.state.health_task = asyncio.create_task(health_check_loop(app.state.session_factory))
  ```
- `finally` 内 cancel：
  ```python
  if app.state.health_task is not None:
      app.state.health_task.cancel()
      with contextlib.suppress(asyncio.CancelledError):
          await app.state.health_task
  ```
- `import asyncio` / `import contextlib` 顶部补上。

后端 `services/control_plane/src/control_plane/routers/services.py`：

- 加新端点：
  ```python
  class HealthHistoryItem(BaseModel):
      ts: datetime
      from_status: HealthStatus | None
      to_status: HealthStatus | None

  class HealthHistoryOut(BaseModel):
      items: list[HealthHistoryItem]

  @router.get(
      "/{slug}/health-history",
      response_model=HealthHistoryOut,
      dependencies=[Depends(require_role("admin", "operator", "viewer"))],
  )
  async def get_service_health_history(
      slug: str,
      limit: int = Query(default=100, ge=1, le=500),
      db: AsyncSession = Depends(get_db),
  ) -> HealthHistoryOut:
      svc = (await db.execute(select(McpService).where(McpService.slug == slug))).scalar_one_or_none()
      if svc is None:
          raise HTTPException(status.HTTP_404_NOT_FOUND, "service not found")
      events = (await db.execute(
          select(AuditEvent)
          .where(AuditEvent.target_type == "mcp_service")
          .where(AuditEvent.target_id == str(svc.id))
          .where(AuditEvent.action == Action.SERVICE_HEALTH_CHANGE)
          .order_by(AuditEvent.ts.desc())
          .limit(limit)
      )).scalars().all()
      return HealthHistoryOut(items=[
          HealthHistoryItem(
              ts=e.ts,
              from_status=(e.before or {}).get("health_status"),
              to_status=(e.after or {}).get("health_status"),
          ) for e in events
      ])
  ```
- import 增加 `Query`、`AuditEvent`、`Action`。

**未覆盖**：

- **多 control-plane 实例的探活并发**：当前 compose 单实例 control-plane，无问题。若未来 scale=2 → 两实例都跑 health loop、双倍写库、audit 行翻倍。修法：用 Redis 分布式锁 (`SET NX EX`) 选一个 leader 执行轮询。本批次不实现，文档化为已知 latent。
- **慢 endpoint 拖累**：concurrency=8、timeout=3s，理论上一轮最多耗 `ceil(N/8) * 3s`。50 个服务 = 19s，仍在 30s 间隔内。100 个服务可能跨轮。本批次不引入"上一轮没结束就跳过这轮"的护栏；如果跑到这一步再优化。
- **`audit_events` 体量随状态抖动膨胀**：状态频繁切换会写很多 audit 行。当前 audit 表无 retention 策略（spec 标注 v2 任务）。worker 不做 hysteresis（如"连续 2 次失败才算 unhealthy"），单轮状态变化即写一行。后续真出现"抖动"问题再加抑制层。
- **健康历史不分页 / 仅 limit=100**：spec §4.3 没要求分页 UI，详情页 tab 当前只展示最近 100 条。后续若有"翻历史更远"需求，加 page/page_size。
- **probe HTTP 方法是 POST，无认证**：探活请求带的是 anonymous POST，被探的 MCP 后端必须**允许无认证 initialize**或返回 4xx。如果后端要求强认证 → 4xx → 我们仍判 healthy（"有响应"）。若强认证返 401/403 也归 healthy；网络层完全断 → unhealthy。语义清晰。
- **不区分 unknown 与 unhealthy**：spec 枚举里有 `unknown`；本实现里 probe 总是给出 healthy/unhealthy 二元结果。初始默认 `unknown` 维持（worker 启动前 / 服务从未被探过的状态）。worker 跑过一次后服务永远落到 healthy/unhealthy 之一。
- **关停 worker 时正在跑的轮次会被 cancel**：lifespan finally 里 `health_task.cancel()` 触发 `asyncio.CancelledError`，可能让某些 update 半截掉。事务尚未 commit 时 cancel → 整轮回滚（asyncpg 行为）；commit 完后 cancel → 已落盘。无脏数据风险。
