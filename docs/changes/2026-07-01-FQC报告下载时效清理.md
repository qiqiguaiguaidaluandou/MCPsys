# FQC 报告下载文件加时效 + 后台清扫

时间窗：2026-07-01。延续 `495b433 feat: 对外暴露 aftersales-search 的 FQC 报告下载`。上一批把「调业务接口拿 base64 → 解码落盘 → 挂在管理系统域名下（nginx `/mcp-files/aftersales-search/` → MCP 容器）给用户下载」的链路打通了，但落盘的报告**永久留存**：`fqc_report.py` 按 `{sn}_{fileName}` 命名，同一 SN 覆盖、不同 SN 无限累积，`aftersales-fqc-reports` 卷只增不减；下载链接也**永不失效**，转发出去的旧链接（文件名含 SN，可枚举）长期可下。

这些报告是**临时产物**——随时能用 SN 重新拉接口再生成，没有唯一副本价值。故引入 TTL：文件/链接默认 2 小时后失效并清理。

条目结构沿用：症状/需求 → 根因/范围 → 改法 → 测试 → 验证 → 未覆盖。

## 1. FQC 报告下载文件加有效期，超时失效并自动清理

**症状/需求**：

- `mcp-services/aftersales-search/src/mcpserver/tools/fqc_report.py` 每次查询把解码后的 Excel 写到 `config.FQC_REPORT_DIR`（容器内 `/data/fqc_reports`，compose 具名卷 `aftersales-fqc-reports` 持久化），**无任何回收**。
- `files.py` 的下载端点 `_download` 只判断「文件存在」，链接**永不过期**。文件名 `{sn}_{fileName}`，SN 已知即可拼出链接、且可枚举。
- 用户需求：生成的文件不长期存储，比如只留 2 小时，之后删除、下载链接同步失效——既控制磁盘膨胀，也让泄露/转发的旧链接自动作废。

**根因/范围**：

- 采用方案：**mtime 判定 + 后台守护线程清扫**，不引调度库。报告清理是纯文件系统操作（`listdir`/`stat`/`unlink`），且 MCP 服务的主体是 uvicorn/starlette，起一个 `threading.Thread(daemon=True)` 最省事，不依赖 starlette lifespan（FastMCP 的 `streamable_http_app` 自带 lifespan 管 session manager，不去掺和它）。
- **两层协作，缺一不可**：
  - 下载端点按 mtime 判过期 → 链接**在满 TTL 那一刻精确失效**，不依赖清扫任务是否恰好跑过。
  - 后台线程周期删过期文件 → **真正回收磁盘**，覆盖「没人来下载、端点从不触发」的文件。只有前者的话，无人问津的文件永远躺在卷里。
- **时间基准用 mtime**，不额外记元数据。副作用：同一 SN 再查会覆盖文件、刷新 mtime = 自动续期，符合直觉，非 bug。
- **不解决枚举**：TTL 只限时效。防猜链接（随机 token 文件名 / 签名 URL）是独立的一件事，本批次不做，文档化为未覆盖。
- 不动 nginx、下载路由前缀、正常下载逻辑，改动纯增量。

**改法**：

`mcp-services/aftersales-search/src/mcpserver/config.py`：

- 新增两个配置：
  ```python
  FQC_REPORT_TTL_HOURS = float(os.getenv("FQC_REPORT_TTL_HOURS", "2"))
  FQC_REPORT_SWEEP_INTERVAL_MINUTES = float(
      os.getenv("FQC_REPORT_SWEEP_INTERVAL_MINUTES", "15")
  )
  ```
- `TTL_HOURS<=0` 语义定为「永不过期」，回到旧行为（也用于关闭本特性）。

`mcp-services/aftersales-search/src/mcpserver/files.py`：

- `_ttl_seconds()` = `TTL_HOURS * 3600`；`_is_expired(path)`：`TTL<=0` 返回 False（永不过期），`os.path.getmtime` 失败按已过期（True）处理。
- `_download` 判断条件加 `or _is_expired(path)`，过期按 404 返回。
- `sweep_expired() -> int`：遍历 `FQC_REPORT_DIR`，删除所有 `_is_expired` 的文件，返回删除数；`TTL<=0` 或目录不存在直接返回 0；`os.remove` 的 `OSError` 吞掉（并发删除/权限，下轮再试）。
- `start_sweeper()`：`TTL<=0` 不启动；否则起守护线程，`interval = max(60, SWEEP_INTERVAL_MINUTES*60)`，循环 `sweep_expired()`（try/except 兜住单次异常，绝不让线程退出，否则磁盘不再回收）后 `time.sleep(interval)`。

`mcp-services/aftersales-search/src/mcpserver/server.py`：

- `files.register(app)` 之后加 `files.start_sweeper()`。

`mcp-services/aftersales-search/.env.example`：记录 `FQC_REPORT_TTL_HOURS` / `FQC_REPORT_SWEEP_INTERVAL_MINUTES`。

`tools/fqc_report.py`：模块 docstring 与工具 `Returns` 补「下载链接有时效（默认 2 小时），过期后失效并被清理，重新查询同一 SN 即可再生成」。

**测试**：

- 本次为纯文件系统 + 线程逻辑，`py_compile` 通过。逻辑用例（建议后续补 `tests/`，直调 `sweep_expired` / `_is_expired`，避免起线程）：
  - 新写入的文件 `_is_expired` 为 False；把 mtime 改到 TTL 之前（`os.utime`）后为 True。
  - `sweep_expired` 只删过期文件、保留未过期，返回删除数正确。
  - `TTL<=0` 时 `_is_expired` 恒 False、`sweep_expired` 返回 0、`start_sweeper` 不起线程。
  - `_download` 对过期文件返回 404、对新鲜文件返回 200。

**验证**（待在测试环境跑）：

1. 把 `FQC_REPORT_TTL_HOURS` 调小（如 `0.02` ≈ 72 秒）、`FQC_REPORT_SWEEP_INTERVAL_MINUTES` 保持或调小，查一次 FQC 报告拿到链接：
   - 立刻点 → 正常下载。
   - 等过 TTL 再点同一链接 → 404。
   - 再过一个清扫间隔，`docker compose exec mcp-aftersales-search ls /data/fqc_reports` → 该文件已被删除。
2. 重新查询同一 SN → 得到新链接、可下载（覆盖 + mtime 刷新）。
3. `FQC_REPORT_TTL_HOURS=0` 重启 → 文件永久留存、清扫线程不启动（回归旧行为）。

**未覆盖**：

- **防枚举**：文件名仍是可猜的 `{sn}_{fileName}`，TTL 只限时效不限访问。若要「只有管理系统登录用户能下」或「链接不可猜」，需随机 token 文件名 / 签名 URL / 走 control-plane 鉴权代理——独立工作，未做。
- **多副本一致性**：`mcp-aftersales-search` 当前单实例、卷独占。若将来多副本共享卷，多个清扫线程会重复扫（幂等、无脏数据，仅浪费）。
- **正在下载时被清扫删除**：Linux 上 `FileResponse` 已打开的 fd 在 `unlink` 后仍可读完（inode 存活），下载不中断；非 Linux 未验证。
- **物理空间回收**：`os.remove` 直接删文件，空间即时释放（非 DB 的 dead tuple 问题），无需 vacuum 类操作。
