## 1. 修复：新建用户失败时只显示「请求失败 (422)」而看不到原因

**症状**：Web 用户管理页点「新建用户」，密码填短（如 `test1`，5 字符）提交后控制台报
`POST /api/v1/users 422`，UI 只弹一条「请求失败 (422)」，看不到「密码至少 8 位」这种字段级原因。

**根因**：两条独立缺陷叠加。

1. 前端 form 校验缺失：`UserListPage.vue` 只做了非空检查，未与后端
   `UserCreate`（`username` 3–64、`password` 8–128、`role` 必填）的约束对齐 →
   非法输入直接打到后端走一圈才被拒。
2. 全局 axios interceptor 错误格式化：`client.ts` 把响应类型声明成
   `AxiosError<{ detail?: string }>`，对 FastAPI 422 的 `detail: []`
   数组形态判 `typeof === 'string'` 一律落空，最终只能展示「请求失败 (422)」。

**改法**：

- 改 `services/web/src/api/types.ts`：新增 `ApiErrorItem`（覆盖 `type/loc/msg/ctx/input`），
  `ApiError.detail` 改成 `string | ApiErrorItem[]`，与 FastAPI 422 实际结构对齐。
- 改 `services/web/src/api/client.ts`：
  - 提取并导出 `formatDetail(detail)`：
    - `string` → 原样返回
    - 数组 → 每条按 `loc 去掉 'body' 前缀后 join('.') + ': ' + msg` 格式化，多条用 `；` 拼接
    - 其他 → 空串
  - interceptor 改用 `formatDetail` 取代旧的 `typeof === 'string'` 判断。
- 改 `services/web/src/views/users/UserListPage.vue`：
  - 引入 `FormInstance` / `FormRules`，新增 `formRef`。
  - 新增 `rules`：`username` 3–64、`password` 8–128、`role` 必填，与后端 Pydantic 约束 1:1。
  - 模板 `<el-form>` 绑 `ref / :model / :rules`，每个 `<el-form-item>` 改用 `prop=`，
    去掉旧的 `required` 静态属性。
  - `onCreate` 改为先 `formRef.value.validate()` 失败即 return，成功后调 `createUser`，
    提交完成再 `formRef.value.resetFields()`。
- 加 `services/web/tests/unit/client.test.ts`：新增 `describe('formatDetail')` 5 例
  （string / undefined / 单条带 body loc / 多条 join；/ loc 缺失或为空回退到 bare msg）。

**验证**：

- `npm run typecheck` 通过
- `npm run lint` 0 errors（仍有 10 条与本次无关的预存 warning）
- `npm test` 22/22（其中 client.test.ts 由 3 例 → 8 例）

**未覆盖**（待后续判断是否成单独条目）：

- `ApplicationListPage.vue` / `ServiceCreatePage.vue` 等其他 form 同样只做了非空校验，
  没和后端约束对齐。此次只修了用户管理表单；其他表单的 422 反馈现在虽然能正确显示字段错误
  （interceptor 通道已修），但仍然存在「前端没拦在客户端、要走后端往返」的体验问题。

## 2. 用户管理：将「编辑」操作换成可用的「删除」

**症状/需求**：用户管理列表当前的「编辑」按钮路由到 `/users/:id`（UserDetailPage），
但后端 `routers/users.py` 实际只有 `POST` 和 `GET (list)` 两个端点，没有 `GET /{id}` 与
`PUT /{id}`，UserDetailPage 一加载就 404、保存也 404 —— 整个编辑流是死的。
用户决定：去掉无用的编辑入口，改为可用的删除入口，并真正实现删除功能。

**根因/范围**：

- 编辑流之所以「显得有功能、实际没有」是因为只在 web 侧搭了 UI，后端 GET/PUT 从未实现。
- 删除选择 **hard delete + IntegrityError 兜底 409**，不做 soft delete：
  - 后端没有 PUT 接口，禁用通道也是空的，soft delete 没基础设施
  - 用户明确要「实际功能」——把 status 设 disabled 还留在列表里不符合直觉
- FK 引用盘点（`packages/mcpsys_shared/.../models.py`）：
  - `applications.owner_user_id`：NOT NULL，默认 RESTRICT → 拥有应用即阻塞
  - `mcp_service_versions.created_by`：nullable，默认 RESTRICT
  - `audit_events.actor_user_id`：nullable，默认 RESTRICT
  - `service_permissions.granted_by`：nullable，默认 RESTRICT
  - 本次**不**改 FK ondelete 语义（属于迁移级动作，越界），FK 命中直接 409 让用户处理。
- ProfilePage 也调 `updateUser` 做密码自助修改 → 同样后端没 PUT、是个 latent bug。
  **不在本次范围**，列入「未覆盖」。

**改法**：

- 改 `services/control_plane/src/control_plane/routers/users.py`：
  - import 增加 `get_current_user`
  - 新增 `@router.delete("/{user_id}", status_code=204, dependencies=[Depends(require_role("admin"))])`
    `delete_user(user_id, current_user=Depends(get_current_user), db=Depends(get_db))`
    - `user_id == current_user.id` → `HTTPException(400, "不能删除当前登录账号")`
    - `await db.get(User, user_id)`，None → `HTTPException(404, "用户不存在")`
    - `await db.delete(user)` + `await db.flush()`；捕 `IntegrityError` →
      `HTTPException(409, "无法删除：用户被应用 / 审计 / 服务版本 / 权限授予记录引用，请先转移或考虑禁用账号")`
    - 正常路径由 `get_db` 自动 commit
- 改 `services/web/src/api/users.ts`：
  - 删除 `getUser`（无后端 GET-by-id，UserDetailPage 也一起被删）
  - 新增 `export function deleteUser(id: number): Promise<void>` → `client.delete('/api/v1/users/' + id)`
  - 保留 `updateUser`（ProfilePage 仍引用，留待后续条目）
- 改 `services/web/src/views/users/UserListPage.vue`：
  - 用户名列：去掉 `<router-link :to="/users/${row.id}">` 包裹，直接渲染用户名（保留 mono 样式 + 「我自己」tag）
  - 操作列：把 `编辑`（`router.push(/users/...)`）换成 `删除`（`type="danger" link`、自身行 `disabled`）
  - 新增 `onDelete(row)`：`ElMessageBox.confirm(\`确认删除用户 \${row.username}？此操作不可撤销。\`, '删除用户', { type: 'warning', confirmButtonText: '删除', cancelButtonText: '取消' })`
    → resolved 后 `await deleteUser(row.id)` → `ElMessage.success('已删除')` → `load()`；
    rejected（用户点取消）静默吞掉
  - import 增加 `ElMessageBox` 和 `deleteUser`，若 `useRouter` 不再被使用则一并移除
- 删除 `services/web/src/views/users/UserDetailPage.vue` 整文件
- 改 `services/web/src/router/index.ts`：删除 `/users/:id` (`UserDetail`) 路由项

**测试**：

后端在 `services/control_plane/tests/test_users.py` 增 5 例：
- `test_delete_user_as_admin`：admin 删一个 viewer → 204；再 list → 不含
- `test_delete_self_forbidden`：admin 删自己 → 400
- `test_delete_user_as_viewer_forbidden`：viewer 删别人 → 403（require_role 拦）
- `test_delete_nonexistent_user`：admin 删不存在 id → 404
- `test_delete_user_with_applications_conflict`：直接 session 里建 `Application(owner_user_id=viewer.id, name=...)` 落库，admin 删 viewer → 409

前端不新增单元测试（UI 流为 element-plus 弹窗 + axios，ROI 低；类型与现有 client.test.ts 覆盖足够）。

**验证**（2026-05-11 执行结果）：

- 后端：`uv run pytest services/control_plane/tests/test_users.py -v` → **9 passed**
  （原 4 例 + 新 5 例：admin 删 viewer / 删自己 400 / viewer 越权 403 / 不存在 404 / FK 冲突 409）
- 前端：
  - `npm run typecheck` → clean
  - `npm run lint` → 0 errors（warning 由原 10 条减为 9 条，UserDetailPage 删除带走一条）
  - `npm test` → 22/22 通过
- 手工验证（待用户在浏览器端跑一遍）：
  ① 自己那行的「删除」按钮禁用
  ② 删一个普通账号：弹确认 → 确认 → 列表刷新去掉该行
  ③ 删一个拥有应用的账号：弹 409「无法删除：用户被应用...」

**未覆盖**：

- ProfilePage.vue 的 `updateUser` 调用对应后端 PUT `/api/v1/users/{id}` **不存在** —— 自助改密码也是死的。
  这是与本条目同源（用户子系统后端只做了 create/list）的 latent bug，独立成下一条小需求或并入 V1-B。
