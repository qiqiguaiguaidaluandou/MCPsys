# 服务归档式删除

时间窗：2026-05-13，V1-D 实施前夕的小需求插队。盘点服务目录"无法删除"问题，落地"归档式删除"语义。

不走 spec/plan。条目结构：症状/需求 → 根因/范围 → 改法 → 测试 → 验证 → 未覆盖。

---

## 1. 服务目录：无法删除服务

**症状/需求**：服务一旦注册就只能 disable（且 UI 上连 disable 按钮都没有），实际部署中存在"测试时建了一堆 slug，正式发布前想清掉"的诉求。直接硬删 (DROP) 又会让 `call_logs` 历史 `service_id` 变孤儿，dashboard `LEFT JOIN mcp_services` 拿不到 slug，丢失"曾经在用"的信息。

**根因/范围**：

- 后端 `routers/services.py:181 delete_service` 已是软删除（`status=disabled`），但**原 slug 仍占用 unique 约束**，无法重建同名服务——这是用户体感"删不掉"的真正痛点之一。
- 前端 `api/services.ts:59 disableService` 函数存在但**全工程零调用**，`ServiceListPage` / `ServiceDetailPage` 都没暴露按钮，因此 UI 上完全没有"删除"入口。
- 硬删除不可取：
  - `call_logs.service_id` 故意设计为无 FK 的 Integer 列以保留历史（`models.py:195`），硬删后历史聚合变孤儿
  - `service_versions.service_id` 有 FK 无 CASCADE → IntegrityError
  - `audit_events.target_id` 字符串引用同样会变孤儿
  - 不可逆，无误删保护
- 选定方案：**归档式**（软删 + slug 重写）。等价 UX = 硬删（用户看不到、能重建同名），数据完整性 = 软删（call_logs/audit 引用全保留）。

**改法**：

- 后端 `services/control_plane/src/control_plane/routers/services.py`：
  - `delete_service` 在 `status=disabled` 之后追加 `svc.slug = f"__archived_{svc.id}"`。`__archived_` 双下划线开头跨过用户 slug 正则（`SLUG_RE = ^[a-z0-9]...`），与用户 slug 命名空间永不冲突；`id` 是 PK 单调递增，归档 slug 全局唯一。
  - 长度：`String(64)` 列；`__archived_` (11 字符) + id (现实下 ≤ 10 位) ≤ 21 字符，远低于上限，不需要截断。
  - **`display_name` 不动**：列 `String(128)`，加 `[已归档]` 前缀虽直观但会触碰 128 长度上限（用户原 display_name 可填满），不值得为视觉提示让逻辑复杂；列表用 `StatusTag` 区分 active/disabled 已经够清楚。
  - `publish_service_invalidate` 调用从 `svc.slug`（已是归档名）改为 `before["slug"]`（原始名）——gateway 缓存以原始 slug 为 key，必须用原值失效。
  - docstring 由 "Soft-delete" 改为 "Archive"，澄清新语义。

- 后端 `services/control_plane/tests/test_services.py`：
  - 改造 `test_delete_service_soft_marks_disabled` → `test_delete_service_archives`：验证原 slug 路径 404、`__archived_{id}` 路径 200、status=disabled、display_name 保留。
  - 新增 `test_delete_then_recreate_same_slug`：归档式删除的核心收益验证——删除后能用同名 slug 重新创建，且新 service 拿到新 id。
  - `test_audit_service_delete` 扩展断言：`before["slug"]` 是原始值、`after["slug"]` 是归档值，确保审计可追溯。
  - `test_delete_publishes_service_invalidate` **不动**：`_drain(ps, "byebye")` 验证 pubsub 收到原始 slug，已经覆盖"用原始 slug 发失效"的逻辑。

- 前端 `services/web/src/api/services.ts`：
  - `disableService` 重命名为 `archiveService`——更准确反映新语义（slug 也会变）。
  - 函数体不变（仍是 `DELETE /api/v1/services/{slug}`），是纯接口名层重命名。
  - 旧名零调用点，rename 零兼容负担。

- 前端 `services/web/src/views/services/ServiceListPage.vue`：
  - import 加 `archiveService`。
  - `filterStatus` 默认值由 `''` 改为 `'active'`——归档项默认隐藏，用户主动切到"禁用"才能看到，符合"删了就不见"的体感。
  - 新增 `deleteDialog` reactive（`visible` / `submitting` / `target` / `confirmInput`）和 `openDeleteDialog(svc)` / `onDelete()`。
  - 操作列宽 80 → 140，加红色 link 按钮"删除"，仅 admin 角色 + `row.status === 'active'` 可见（已归档项不再显示删除入口）。
  - 新增 `<el-dialog>` 删除确认弹窗：
    - `el-alert` 解释归档语义（slug 会变 `__archived_{id}`、原 slug 释放、call_logs 保留可追溯审计）
    - 要求用户在 `el-input` 中**完整输入 slug** 才能确认；输入不匹配时确认按钮 disabled
    - 与现有"注册新服务"对话框风格一致

**测试**：

- 后端：`uv run --package control-plane pytest services/control_plane/tests/test_services.py -v` → 14 passed（含改造 1 例 + 新增 1 例 + 扩展 1 例）。
- 前端：`pnpm typecheck` → clean。
- 前端 UI 流（element-plus 弹窗 + axios）沿用 2026-05-12 批次的判断不写单测，ROI 低。

**验证**（待用户在浏览器端跑一遍）：

1. admin 登录 → 服务目录 → 列表默认只显示 active 服务
2. 选 active 服务行 → 点红色"删除"按钮 → 弹确认对话框
3. 输入框留空 / 输错 slug → "确认删除"按钮保持 disabled
4. 完整输入正确 slug → 按钮可点 → 确认后 toast "服务 xxx 已归档" → 列表行消失
5. status filter 切到"禁用" → 看到归档项，slug 显示为 `__archived_{id}`、display_name 保留原值、状态标签"禁用"
6. 重新注册一个使用刚归档的 slug → 成功创建（关键回归点）
7. viewer 角色登录 → 删除按钮不可见
8. 已归档项（status=disabled）不再显示删除按钮（避免归档套娃）
9. `GET /api/v1/audit-events` 能看到 `service.delete` 事件，before.slug=原值、after.slug=归档值

**未覆盖**：

- **服务详情页删除入口**未加：详情页处于"管理某个具体服务"的语境下，加删除按钮会让"误删本服务"的概率上升，且不同于列表的"批量管理"语义。如需补可单独条目，模板复制本批次的 deleteDialog 即可。
- **恢复/反归档**功能：归档后只能通过 DB 手工改回（`UPDATE mcp_services SET status='active', slug='xxx' WHERE id=...`）或后续做个 admin-only 的"恢复"API。本批次不实现，避免范围扩张；实操中误删后从审计 before 快照可拿到原 slug。
- **service_versions / service_permissions 归档行为**未显式约束：
  - `service_permissions.service_id` 有 `ondelete=CASCADE`，但归档**没有 DELETE**，所以权限授予记录会保留指向归档服务——当前未发现负面影响，但若后续允许重建同名服务时复用 grants，需要做迁移决策。本批次不动。
  - `service_versions` 同理，全部保留。
- **dashboard "Top services" 显示归档 slug**：V1-D plan 会重写 dashboard 用 stats/breakdown 端点，那里再决定是否过滤 `status=disabled`。本批次不动。
- **限流/健康检查 worker** 是否会继续 poll `__archived_*` 服务：endpoint_url 仍在、status=disabled，需后续 check 健康检查任务是否按 status 跳过；若不跳过会有无谓的 outbound 请求。本批次未验证。
